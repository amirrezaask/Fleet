## Area

`skills/factory/`, whose stages run as `/factory <stage>` subcommands,
owns the opt-in delivery pipeline: intents, designs, plans, debriefs, reviews and
task metadata. Factory is self-contained: it carries its own guide for keeping
specifications true and the area and workflow templates it needs.

Requirements R1-R10 were amended on 2026-11-02 by ADMIN's request to adopt the AI-native
SDLC pipeline (task `factory-sdlc-pipeline`), and R4, R5, R9 and R10 again the same day for
the flat task layout; R4 was amended once more that day to move tasks into `.factory/`
with their reviews, and R4, R9 and R10 a third time (2026-11-03) so a task keeps a stable directory name and records its status in `TASK.html`; R4, R5, R7 and R10 were amended again on 2026-11-03 by ADMIN's request to return every document to Markdown, reviewed with `md <file>`. Factory was removed on 2026-11-19 and restored on 2026-11-21 by ADMIN's request ("restore our factory skill, just remove the TASK.md file, everything else stays the same"): R4, R5, R9 and R10 were amended that day to keep tasks in the agent memory vault, drop `TASK.md` and read a task's state from its documents; the task board is not restored. The earlier text is in Git history.

## Requirements

- **R1:** Given any request, when no `/factory` command (with or without a stage subcommand) was typed, then Factory does not run and no task is created; every Factory skill declares `disable-model-invocation: true` and `allow_implicit_invocation: false`. Research alone never authorizes implementation.
- **R2:** Given a Factory task, when it moves through the pipeline, then the stages are Intent, Design, Plan, Build and Review, in that order (amended 2026-11-03 by ADMIN's request: Test is merged into Build and Review is new); each stage ends by committing its artifact and the next starts by reading it. Design may be skipped only with the reason recorded in the intent.
- **R3:** Given the gates, when leaving Intent or Design, then the user's approval is required and recorded; running the next stage's command counts as approval. The plan needs no human approval but must pass its self-check and be committed before any implementation.
- **R4:** Given a task, when its documents are written, then `~/.agents/projects/<project>/tasks/<NNN>-<task-name>/`, in the agent memory vault outside the repository and shared by all worktrees, where `<project>` is the main checkout's path relative to home, (a three-digit, zero-padded sequence number, one more than the highest sibling, taken under the shared `~/.agents/.git/factory-claim.lock`, so directories sort in creation order) holds `INTENT.md`, optional `DESIGN.md` with its artifacts in a `design/` folder next to the `subtasks/` folder, `PLAN.md`, `DEBRIEF.md` and the review `REVIEW.md`, with raw evidence in a gitignored `evidence/` folder; the vault's Git history holds the documents' history, and the store replaces `docs/tasks/` and the in-repository `.factory/`. A task has no `TASK.md` or other metadata file: its stage is the latest stage document it holds (`INTENT.md` intent, `DESIGN.md` design, `PLAN.md` plan, `DEBRIEF.md` or `REVIEW.md` build), it is done only when `REVIEW.md` records `**Review verdict:** PASS`, and a blocker is recorded in the document of the stage it stops. The directory name never changes, and there are no status directories. `TASK.md` files written earlier stay in place and are not read. Intent, design and the report's first screen are short and written for the user; plan and debrief are complete and written for agents. Legacy `BRIEF.*` files count as the intent, and legacy HTML task documents stay readable; when both formats exist the Markdown file is canonical.
- **R5:** Given delivery resources, when resolving templates, then the intent, design, plan, debrief and review templates each have one canonical Markdown file in `skills/factory/templates/`, next to copies of the area and workflow specification templates Factory uses.
- **R6:** Given a plan, when it is written, then it names the files that change, the ordered work, risks, an interrogation (what could break, riskiest step, rejected options), and a test plan that maps every requirement to tests, each tiered `fast` or `heavy`, before any code exists. A bug fix starts with a committed failing test that the fix does not edit.
- **R7:** Given build, when implementation departs from the plan, then the plan is revised before the departing code is committed; requirements and accepted design decisions change only with the user's recorded authorization. Build ends with every `fast` test passing, regression and acceptance evidenced, the plan's `heavy` gates run once as the last step of Build, and `DEBRIEF.md` and `REVIEW.md` written.
- **R8:** Given Build's verification and Review, when verifying, then regression runs first, then acceptance with evidence per requirement, then heavy gates last; Review then runs four independent fresh-context reviewers in parallel (code, security, UI, UX; UI and UX skipped with a recorded reason when no interface changed), whose findings are verified, fixed or accepted, and recorded in `REVIEW.md`. Only the managing agent runs heavy gates and Review. Checks record observed results; a passing suite alone does not prove coverage.
- **R9:** Given task closeout, when declaring completion, then every requirement is evidenced, the debrief and review exist, affected specs match verified behavior, and `REVIEW.md` records `**Review verdict:** PASS`. A manually written verdict does not establish these facts. Out-of-scope findings worth doing become lines in the project's `backlog.md`.
- **R10:** Given a task with separable parts, when creating subtasks, then each is a directory `<task>/subtasks/<NNN>-<subtask>/`, numbered within its parent, with the same documents, nests to any depth, needs no approval from the user for its intent, and refines but never contradicts its parent. A subtask built in its parent's integration branch is done when its `PLAN.md` records `**Merged:** <sha>`, and its dependencies on siblings are listed in its `INTENT.md`. A task reaches `done` only after all descendants are done and its own Review passes. On resume, the agent reconciles the stage documents, specs and the Git diff before continuing.
